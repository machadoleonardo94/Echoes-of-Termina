# Two-button interface — evaluation

Scope: what the two buttons can express on this hardware, what was measured on the
bench board while building it, and where the current provisional mapping does not
hold up. Everything below is grounded in a serial capture of real presses, not in
a design sketch: the raw logs are `.pio/_btn_test.log` (diagnostic round) and
`.pio/_btn_final.log` (production round, both modes).

**Pictures:** `docs/diagrams/button-state-machine.png`, `gesture-map.png` and
`feedback-paths.png` (SVG next to each, for zooming). They are generated by
`tools/make_flowcharts.py`, which also self-checks its own layout — see section 10.

---

## 1. What was built

The single button's logic was replaced by two layers, so the interface can be
argued about without touching the state machine:

| file | role |
| --- | --- |
| `src/services/buttons.h` | pin levels → debounced gestures. Knows nothing about audio, WiFi or LEDs. Per-button click window (see section 9). |
| `src/services/controls.h` | gesture → feature. **The only file that decides what a gesture means.** |
| `src/services/audio_cues.h` | tones mixed into the Bluetooth PCM stream (feedback channel 1). |
| `src/services/ui_feedback.h` | the strip as an overlay: volume bar, animation blink count, mode-switch acknowledgement (feedback channel 2). |
| `src/services/wifi_portal.h` | gained a small facade (`audio_next_track`, `audio_restart_track`, `audio_set_volume_percent`, `audio_is_playing`, …) so the action layer never reaches into the player's internals. |
| `src/services/readings.h` | button code removed; keeps the ADC only. |
| `src/services/mode_manager.h` | no longer hard-codes the Bluetooth volume at boot; `controls_begin()` applies the persisted level to whichever backend came up. |
| `src/services/buttons.h` (`BUTTON_TRACE`) | diagnostic build: logs every raw edge plus a 5 s idle-level census, and suppresses the destructive actions. |

What went away: one pin, a shared press counter with four meanings, a 1000 ms
wait-and-see window, an `ISR`-vs-poll story spread over three files, and
`struct_buttonState`.

### Gesture ladder (per button)

```
MIN_PRESS   < 50 ms   electrical blip, discarded, leaves an open burst alone
CLICK       short press, released before 600 ms, no further press within 400 ms
DOUBLE      2 presses in one burst
TRIPLE      3 presses in one burst
HOLD        still down at 600 ms → then REPEAT every 150 ms → RELEASE on letting go
VERY_LONG   still down at 4000 ms, and it stops the repeat train
```

A hold swallows the burst it interrupted: press-press-hold is a `HOLD`, never a
`DOUBLE` followed by a hold.

## 2. Verified on hardware

Bench board, `echoes-v1` (8 MB, PSRAM disabled), flashed over OTA; both buttons
exercised by hand with COM7 capturing.

**Input layer — works, on both pins.**

```
[BTN] PROG on GPIO0, active LOW (press to GND) — idle level released
[BTN] EXT on GPIO4, active HIGH (press to 3V3) — idle level released
[BTN] levels: PROG(GPIO0)=HIGH EXT(GPIO4)=LOW          ← 5 s census, both idle correctly
[BTN] EXT raw -> PRESSED @29351 ms / released @29516 ms → [BTN] EXT click (165 ms)
[BTN] EXT double (118 ms)      [BTN] EXT triple (92 ms)
[BTN] PROG hold (600 ms)  →  repeat (750) (900) (1050) …  →  release (2783 ms)
[BTN] PROG very-long (4000 ms)
```

* **Zero** `ignored … blip` lines and zero phantom events across ~15 minutes on
  both pins. The old GPIO0 noise problem did not reappear, but the strip was not
  driving hard audio at the time — the polling design is what protects against it.
* Measured human tap durations: **96–190 ms** (PROG 122–157, EXT 124–190). The
  50 ms blip floor therefore has a 2–4× margin, and no tap ever approached the
  600 ms hold threshold. The thresholds are correctly placed on this hardware.
* Burst separation measured: two taps 273 ms apart → `DOUBLE`; three taps 300 and
  346 ms apart → `TRIPLE`; taps 1.5 s apart → three separate `CLICK`s. The 400 ms
  window is doing exactly what it claims.

**Both playback backends.**

| gesture | WiFi mode (local SD player) | Bluetooth mode (phone) |
| --- | --- | --- |
| PROG click | `[BUTTON] No track to pause` (nothing loaded) | `AVRCP pause` / `AVRCP play`, phone confirmed (`phone playback status -> 1/2`) |
| EXT click | `[CTRL] next: no playlist loaded` | `[CTRL] AVRCP next` — track changed |
| EXT double | `[CTRL] LED animation -> none/envelope/fft` | same |
| PROG triple | `[MODE] Switching to Bluetooth — restarting…` → rebooted, phone auto-reconnected | (reverse) |
| PROG/EXT hold | volume ramp 100→0 %, persisted | audible ramp 100→55 →100 %, `A2DP step 127→69→127` |

**Three defects the log exposed, all fixed and rebuilt:**

1. **NVS write per ramp tick.** A 2 s hold wrote flash 13 times
   (`Volume saved to NVS` every 150 ms). Now the ramp persists on its first tick
   and once on release — 2 writes per gesture — and rebooting actions persist
   first, so a 4 s hold that ends in a reboot cannot come back at the pre-hold
   level.
2. **Limit spam.** Holding a button already at 0 %/100 % logged one line every
   150 ms. Now it reports the limit once per gesture (re-verified: one line, then
   12 silent repeats).
3. **Two owners of the volume.** The portal's slider and the button ramp each kept
   their own idea of the level, so a slider move followed by a button press wrote
   the stale value back. There is now one percent, one writer, one NVS key.

**One observation to watch:** `ASSERT_WARN(1 9), in lc_task.c at line 1409` from
the Bluetooth controller, once, immediately after an AVRCP pause while streaming.
It is a warning, not a panic — the session continued normally. Not from this
firmware, but it is worth recognising if it ever shows up alongside a dropout.

## 3. Constraints the interface has to live inside

These are properties of the board and the libraries, each confirmed in this
session or in the library source. They are what make the interface design
non-obvious.

1. **A tap costs 400 ms before it does anything.** A single click cannot be
   committed until the multi-click window closes. Measured consequence: every
   play/pause press is felt ~0.4 s after the finger leaves the button. This is the
   price of having double- and triple-click mean something.

2. **The two modes are exclusive, and the same gesture has two backends.**
   Bluetooth = the phone is the transport (AVRCP only: no playlist, no seek, no
   exact restart). WiFi + standalone = the SD player is the transport, but
   playback **requires the radio down** (no PSRAM on this board: BT mode leaves
   ~42 KB free, WiFi mode ~88 KB, and lwIP plus the decoder do not fit together).
   So while a local track plays there is no portal, no OTA, and no AVRCP — and the
   button path back (`EXT` very-long → `wifi_enable()`) is not a nicety, it is the
   only exit that does not reboot.

3. **AVRCP commands block the main loop for ~100 ms each.** The library's
   `execute_avrc_command()` sends PRESSED, `delay(100)`, RELEASED
   (`BluetoothA2DPSink.cpp:1353-1372`, `delay_ms` is Arduino `delay`). Fine for a
   tap; fatal for a volume ramp, which is why the ramp drives the sink's local
   attenuation with `set_volume()` (no blocking) instead of `volume_up()`.

4. **Who owns the volume is genuinely ambiguous in Bluetooth mode.** Our
   `set_volume()` sets local digital attenuation *and* notifies the phone of the
   new level (`volume_set_by_local_host`); the phone's own slider arrives as
   `SET_ABSOLUTE_VOLUME` and lands in the same `s_volume` (`volume_set_by_controller`).
   Last writer wins. Measured: the button ramp is clearly audible, but a phone
   sitting at 20 % still caps the ceiling no matter what the ramp does.

5. **The local player cannot be created in Bluetooth mode** — `Audio`'s
   constructor installs `I2S_NUM_0`, which the A2DP sink already owns. The old
   firmware allowed a long-press "standalone show" in Bluetooth mode; that is now
   refused explicitly rather than half-executed into silence.

6. **`ESP32-audioI2S` has no mixing hook.** Nothing can be played *on top of* a
   local track, so audio cues behave differently in the two modes (section 5).

## 4. Evaluation of the provisional mapping

```
gesture            PROG (GPIO0)                  EXT (GPIO4)
click              play / pause                  next song
double             restart song                  cycle LED animation
triple             switch mode (reboots)         standalone show
hold + repeat      volume down                   volume up
very long (4 s)    reboot the board              bring WiFi back
```

**What holds up.** Hold = volume on both buttons is the best part of this map:
symmetric, memorable, no modes to learn, and it is the one gesture where
continuous input is the natural expression. Click = play/pause and click = next is
the industry-standard pair. Keeping the rare, destructive actions on the two
hardest gestures (triple, 4 s hold) means neither can be triggered by a pocket
squeeze or a dropped device.

**What does not hold up.**

* **P1 — the 400 ms tax is charged to the most frequent action.** Play/pause is
  the gesture a user makes most and feels most. It waits the longest. Mode switch
  (rare, rebooting, 8 s of silence) is what forces that wait.
* **P2 — the transport row is dead exactly where the device is reachable.** In
  WiFi mode with nothing loaded, a click does nothing but log
  (`No track to pause`, `no playlist loaded`). That is the state the device sits
  in when its owner walks up to it: idle, portal up. The most useful click there
  is "play something", not "pause nothing".
* **P3 — "switch animation" is a blind action.** Tapping EXT twice cycles
  none → envelope → fft, and the only confirmation is a serial line. Envelope and
  FFT do not differ visibly until audio is playing, so a user can cycle three
  times and have no idea where they landed. Same for the volume: with nothing
  playing, a ramp is completely silent and invisible.
* **P4 — "restart" is ambiguous, and both readings already share one button.**
  Double-click = restart the current song; 4 s hold = reboot the device. In
  Bluetooth mode "restart song" degrades to `AVRCP previous()`, which is the
  source app's decision, not ours — it may restart, or step back a track.
* **P5 — the very-long tier has no arming feedback.** Nothing tells the user that
  holding past 4 s is different from holding for 1 s, so the only way to learn it
  is to search for it. On a device whose entire output is a LED strip and a
  speaker, that is a missed opportunity — see section 5.
* **P6 — one button carries five gestures, the other five.** Fine on paper, but
  PROG is also the boot-strapping pin (holding it during a reset enters the ROM
  loader) and on the bench board it is the harder button to reach. Legibility
  would improve if the multi-click ladder lived on the accessible button only.

## 5. Audio feedback: what is actually possible

The device has a speaker, so "the interface talks back" is not decoration — with
no screen it is the only way some actions can be confirmed at all.

**Bluetooth mode — cues can be mixed into the stream. Feasible, and there are two
insertion points.** The library calls its hooks inside `audio_data_callback`
(`BluetoothA2DPSink.cpp:1311-1349`) in this order:

```
raw_stream_reader(data, len)          ← BEFORE volume control  (already used: the LED tap)
volume_control()->update_audio_data((Frame *)data, len / 4)
stream_reader(data, len)              ← AFTER volume control
write_audio(data, len)                → I2S
```

The buffer is mutable — the library itself casts it to `Frame*` and rewrites it in
place for both the channel swap and the volume — so a cue generator can add into
it. Two deliberate choices follow:

* **post-volume hook** (`set_stream_reader(cb, /*is_output=*/true)`): the cue is
  always audible at the same loudness, independent of the volume setting. This is
  the right place for "animation switched", "mode switch armed", "no source
  connected".
* **pre-volume hook**: the cue's loudness tracks the volume, which is exactly what
  a *volume* cue should do — the beep tells you how loud the output actually is,
  which is the one thing a volume ramp cannot otherwise communicate while silent.
* Caveat: `set_stream_reader()`'s second argument **is** `is_output`; passing
  `false` silences the DAC. This is already documented in `mode_manager.h` and is
  the reason the LED tap uses `set_raw_stream_reader()` instead.
* Cost: a precomputed sine table (a few hundred bytes of `static` data) and a
  couple of adds per frame on the BT data path, with ~33 KB free heap in that
  mode. No allocation, no blocking call — unlike AVRCP, which blocks 100 ms.

**WiFi / standalone mode — no cue can be mixed into a playing track.**
`ESP32-audioI2S` owns `I2S_NUM_0` and has no beep or mixing API. The options, in
order of preference:

1. **Use the strip as the feedback channel.** 144 addressable LEDs, already
   driven, works in both modes, costs nothing on the audio path. A volume ramp
   becomes a bar that fills as you hold; an animation switch becomes a short
   confirmation flash; a 4 s hold becomes a countdown; the mode switch becomes a
   colour. This is the highest-value change in this document, and it is mode
   independent.
2. **Short cue files from the SD card** — only usable between tracks or while
   idle (playing one means re-connecting the decoder to a different file, which
   stops the song), so it cannot serve volume or transport feedback mid-track.
3. **Accept silence** for local playback, and keep serial lines for development.

**Consequence for the feature list.** "Play" and "pause" are inherently audible
(the music starts and stops). "Next song" is audible in Bluetooth mode and
self-evident in local mode. **Volume, animation and mode switch are the three that
need help**, and they need it in both modes — which points at the strip for all
three, with in-stream cues in Bluetooth mode as the refinement that makes volume
feedback honest.

> Superseded in one respect by section 11: the board's *own* states (waiting for a
> phone, paired, hotspot, WiFi up/down) happen with no stream in existence, so a third
> path was added — tones written straight to the I2S wire while the DMA has no writer.
> A track that is already playing is still unreachable; that conclusion stands.

## 6. Options for the mapping

**Option A — keep it, tune it.** Leave the map as-is and drop the multi-click
window from 400 ms to 300 ms. Lowest risk, does not fix P1–P5.

**Option B — per-button windows (recommended).** Make the multi-click window a
per-button property, so a button whose clicks are single-purpose fires them
*immediately on release* instead of waiting:

```
PROG (single-purpose, instant)     EXT (laddered, 400 ms window)
click      play / pause            click      play-when-idle, else next song
hold       volume down             double     cycle LED animation
very long  reboot                  triple     switch mode (reboots)
                                   hold       volume up
                                   very long  bring WiFi back
```

This fixes P1 (pause is instant), P2 (the idle click starts a show rather than
aiming at nothing), and P6 (the hidden gestures concentrate on the accessible
button). It costs ~15 lines in `buttons.h`: a `multi_gap_ms` field per wiring
entry, with 0 meaning "commit the click on release".

**Option C — chord for the mode switch, everything instant.** Hold *both* buttons
for 3 s → switch mode, with the strip counting down. Then neither button needs a
multi-click window and every click is instant. The ramps cancel out naturally
during the chord (one steps up, one steps down in the same 150 ms tick), so no
extra arbitration is needed. The risk is an accidental chord — which is why the
countdown on the strip is not optional, and why this is the second choice: it buys
responsiveness by making a rebooting action easier to trigger by accident.

**Recommendation: B now, C only if the 400 ms tap lag on EXT also turns out to
annoy.** Both are cheap; B subsumes the immediate fix and leaves the chord open.

## 9. What was implemented after this evaluation

### The map that ships

```
PROG (GPIO0) — single-purpose, clicks are instant (no multi-click window)
    click        play / pause   (with nothing loaded: play = start a standalone show)
    hold         volume down    (ramp, strip bar, rising/falling ticks)
    very long    restart the current song (the ramp is undone first)

EXT (GPIO4) — carries the ladder, clicks wait for the 400 ms window
    click        play when idle, otherwise next song
    double       cycle LED animation (1/2/3 blue blinks = which animation)
    triple       switch mode (3 white flashes, then the reboot)
    hold         volume up      (same feedback as PROG's ramp)
    very long    bring WiFi back after a standalone show tore it down
```

### The two feedback channels

| channel | file | works when | cannot do |
| --- | --- | --- | --- |
| tones mixed into the A2DP stream | `src/services/audio_cues.h` (`cue_mix`) | Bluetooth mode, **while audio is actually flowing** | anything in local playback; anything while the phone is paused or no source is connected (no data callback = no stream to mix into) |
| tones written straight to the I2S wire | `src/services/audio_cues.h` (`cue_wire_pump`, `cue_play_now`) | every state with no stream: Bluetooth waiting/paired, WiFi hotspot/connected/failed | while a track or a phone's stream owns the DMA (section 11) |
| the strip as an overlay | `src/services/ui_feedback.h` | both modes, always | show fine detail (it is a bar and a blink count) |

Measured reasons each is placed where it is:

* The cue mixer registers through `set_stream_reader(cue_mix, true)`, i.e. **after**
  volume control, so a cue is equally loud at 5 % and at 100 %. That is the right
  behaviour for "the animation changed", and it is why the *volume* cue reports the
  level by **pitch** (400 Hz → 1400 Hz) rather than by loudness.
* The overlay pre-empts both LED renderers. `run_lightshow()` and
  `run_led_animation()` consult `ui_feedback_active()` and stand down, because each
  renderer ends its frame in `majora.show()`, which blocks for the whole RMT
  transfer (~29 µs/LED, ~4 ms at 144 LEDs). Two renderers drawing the same frame
  would halve the frame rate for no visible gain.
* The ramp's strip bar refreshes on every tick (150 ms) and is deliberately not
  frame-paced, or the bar would visibly lag the finger on a long strip.
* `ui_flash_blocking()` (the mode-switch acknowledgement) blocks ~0.9 s on purpose:
  the action it confirms is about to take the CPU away, and a user who does not see
  the acknowledgement cannot tell an accepted triple-click from a missed one.

### Decisions taken while implementing

* **A very-long hold undoes the ramp it interrupted.** The gesture starts as a
  volume ramp and only becomes "restart" at 4 s; without the undo, restarting a
  song would also have dragged the volume to one end.
* **The Bluetooth→WiFi direction is the only one with an audible mode-switch
  cue.** The arpeggio is mixed into the A2DP stream, and that stream exists only
  while Bluetooth mode is up — switching *to* Bluetooth happens with the mixer off.
  Both directions get the white flashes.
* **The diagnostic build suppresses two actions, not three**: mode switch and
  play-from-idle (which tears WiFi down). A reboot gesture no longer exists to
  suppress.
* **`ctrl_reboot()` was removed** rather than left unused: the feature list asks for
  restart-the-song, and dead code that reboots a board is not worth keeping for
  nostalgia.
* `lightshow_frame_period_ms()` lost its `static`, because the overlay (included
  above the renderers so they can yield to it) paces its frames with it.

## 11. State cues — the board says what it is doing

Gesture feedback answers a press. It says nothing about the far more common question:
**what is this thing doing right now?** In Bluetooth mode the answer used to be
unavailable everywhere — dark strip, silent speaker, and no way to tell "waiting for a
phone" from "hung". Five states now announce themselves.

### What each one sounds like, and why

| state | kind | motif | where it is triggered |
| --- | --- | --- | --- |
| Bluetooth mode, no source | `CUE_BT_WAIT` | two long low notes rising (D5→G5, 260 ms) | `setup_bluetooth_mode()`, immediately after `a2dp_sink.start()` — **once per boot** |
| source connected | `CUE_BT_PAIRED` | three fast notes, 880→1175→1568 Hz | `cue_on_bt_connection_state()` → `CONNECTION_STATE_CONNECTED` |
| config hotspot created | `CUE_AP_UP` | the same note twice, 60 ms apart | the WiFiManager `setAPCallback()` in `wifi_settings.h` |
| WiFi up | `CUE_WIFI_OK` | rising triad ending high | `setup_WIFI()` on success, and `wifi_enable()` when the 4 s hold works |
| no network | `CUE_WIFI_FAIL` | falling triad ending low | `setup_WIFI()` on portal timeout, and `wifi_enable()` when it cannot reconnect |

One rule makes the set learnable after two or three encounters: **rising = on, falling
= no, a repeated note = "listen, I need something"**. The state motifs also sit in a
different register from the transport cues, so "paired" cannot be mistaken for
"playing".

Three decisions worth recording:

* **"Waiting" plays once, not forever.** A repeating beacon would answer "is it even
  on?" better, but it is also the sound a user would hate by day two. The owner chose
  once-at-boot; the change of state gets announced instead.
* **Disconnect is silent on purpose.** `set_auto_reconnect(true, 3)` cycles through
  `DISCONNECTED` up to three times, so an announcement there would stutter.
* **A cue is never lost to ordering.** `ctrl_switch_mode()` and `ctrl_wifi_restore()`
  call `cue_play_now()` (render here, return when done) because both are followed by
  blocking work — three flashes, or a reboot — that would starve the loop pump.

### Why a second sink was needed

The stream mixer can only speak while the phone is *sending audio*, which is exactly
never in the four states above. What makes the cues possible is the shape of the A2DP
sink itself:

* `a2dp_sink.start()` → `init_i2s()` → `out->begin()` → `i2s_driver_install(I2S_NUM_0)`
  (`BluetoothA2DPSink.cpp:231-237`, `BluetoothA2DPOutput.cpp:74-104`) at 44100 Hz /
  16-bit / stereo with `tx_desc_auto_clear=true` — the DAC is clocked and fed silence
  from boot.
* The base `BluetoothA2DPSink` has **no I2S task**: `i2s_task_handler()` and
  `bt_i2s_task_start_up()` are empty dummies meant for `BluetoothA2DPSinkQueued`
  (`BluetoothA2DPSink.h:603-605`). PCM reaches I2S only from `audio_data_callback()`.

So until a source streams, the DMA has no writer and the wire belongs to the firmware.
The cue engine (`services/audio_cues.h`) renders the **same** `CuePattern` table into
`i2s_write()` for that window, from one dedicated voice, so a cue is identical whichever
sink carries it.

Rules that keep this safe:

* **The gate is the AUDIO state, not the connection state.** `handle_connection_state()`
  publishes `CONNECTED` *before* invoking our callback, so gating on
  `is_connected()` would silence the one cue that matters most. The wire is free while
  `get_audio_state() != STARTED`.
* **In WiFi mode the peripheral is installed per cue.** The decoder is created lazily
  (`wifi_portal.h:_ensure_player`), so nothing owns `I2S_NUM_0` at boot — the cue
  installs it, plays, and uninstalls, which is the sequence the boot beep test already
  proved on both boards. Its DMA is 2 KB, not the decoder's 32 KB, and a silent tail is
  pushed before the uninstall so a cue never ends in a click.
* **One request, one render.** `cue_play()` drops a request into a single slot; both
  sinks claim it under one critical section, so it is rendered exactly once. The pump
  checks that the wire is free *before* claiming, so a cue requested while music plays
  is left for the mixer instead of being consumed and lost.
* **The volume cue stays pitch-coded.** The wire path bypasses the sink's volume
  control entirely, so a cue written there is the same loudness at 0 % and at 100 % —
  correct for a status beep, useless for reporting a level, which is why
  `CUE_VOLUME_TICK` still reports the level as pitch (400→1400 Hz).
* **Nothing here is heard in local playback.** `ESP32-audioI2S` owns the DMA while a
  track runs and has no mixing hook, so `cue_play()` is a no-op in WiFi mode and the
  strip remains the channel for gestures there.

## 12. "Next song" walked a one-entry playlist

**Symptom reported from the bench board:** with a standalone show playing off the SD
card (WiFi mode), an EXT click **restarted the same song** instead of moving to the
next one.

**What the log said** (`.pio/_next_bug.log`, pre-fix):

```
[Lightshow] t=96000 ms  fired=461  next=96043 ms  period=5 ms  leds=28
[BTN] EXT click (125 ms)
[AUDIO] SD file 4331564 bytes, first4=49 44 33 04 (ID3=1 MP3sync=0)
[PORTAL] Playing: /Echoes/Lightshows/wisdom/wisdom.mp3
[AUDIO] play_index -> running=1 rate=48000 ch=2 bits=16 dur=0 s size=4331564
[Lightshow] Attaching /Echoes/Lightshows/wisdom/wisdom.echoes
[Lightshow] t=0 ms  fired=0  next=2000 ms  period=5 ms  leds=28
```

The transport was right — `_play_next()` ran, the file was re-opened, the show was
re-attached — but the *index it moved to was index 0 of a one-entry list*.

**Cause.** `_play_path()` built `playlist` from the **parent folder** of the track it
was given, and the card's layout is one song per Lightshows project
(`/Echoes/Lightshows/<project>/<song>.<ext>` + `<song>.echoes`). So
`playlist.size() == 1`, `_play_next()` computed `index + 1 == 1`, `_play_index()`
wrapped it to `0`, and the same file started again from the top with its lightshow
restarted at t=0. Three projects on the card, and the transport could only ever see
one of them.

**A second, quieter face of the same bug** was visible in the same capture: every
track looped itself at its natural end. `wisdom.mp3` is 270.7 s, the reset happened at
`t=270000 ms`, and `audio_eof_mp3()` → `player_eof` → `_play_next()` hit the identical
wrap. 240 s of capture showed one song playing twice, and a click was *not* required
to reproduce it — which is also why the report ("a click resets the song") was
plausible but the mechanism was not the click.

**Fix** (`src/services/wifi_portal.h`). When the current folder IS a Lightshows project
folder — a direct child of `/Echoes/Lightshows` — and it holds at most one playable
track, the playlist is widened to **one track per project, sorted by path**
(`_build_lightshows_playlist()`, capped at `PLAYLIST_MAX_TRACKS` = 128 with a log line
when the cap is hit). A folder that holds several songs keeps the per-folder list, so
`/Echoes/Music` (three songs, flat) behaves exactly as before. `_play_next()`,
`_play_prev()` and the end-of-track advance are untouched — they simply have
somewhere to go now:

| case | playlist before | playlist after |
| --- | --- | --- |
| a Lightshows project folder (1 song) | `[wisdom.mp3]` | `[changing_seasons.mp3, lost_woods.mp3, wisdom.mp3]` |
| `/Echoes/Music` (3 songs) | its 3 songs | its 3 songs |

Sorted order means `changing_seasons → lost_woods_stereo → wisdom → wrap`, and the
`[PORTAL] Playing:` line now reports the position (`(track 2/3)`) so a skip can be
confirmed from the serial log alone.

**Verified after the OTA flash** (`.pio/_next_fixed.log`):

```
[BTN] EXT click (102 ms)
[CTRL] nothing loaded — starting a standalone show
[SHOW] Standalone: /Echoes/Lightshows/changing_seasons/changing_seasons.mp3  +  .../changing_seasons.echoes
[PORTAL] Playing: /Echoes/Lightshows/changing_seasons/changing_seasons.mp3  (track 1/3)
[BTN] EXT click (115 ms)
[PORTAL] Playing: /Echoes/Lightshows/lost_woods_stereo/lost_woods.mp3  (track 2/3)
[Lightshow] Attaching /Echoes/Lightshows/lost_woods_stereo/lost_woods_stereo.echoes
[Lightshow] Streaming /Echoes/Lightshows/lost_woods_stereo/lost_woods_stereo.echoes  (first command at 3429 ms, heap 28 KB free)
```

Two clicks, two different songs, and the second song brought **its own** lightshow
(28 KB free after the swap — the load fits while a track is streaming). The click is
still silent in local playback for the reason in section 11, so the change of song is
its own confirmation.

**Note for whoever measures next:** the widening happens while the radio is down
(~86 KB free at build time, 127 KB after `wifi_disable_for_show()`), so the extra
`String`s are cheap there — but `_play_index()` runs the swap *while streaming* with
~31 KB free, which is why the list is built once at play time and never rebuilt on a
skip.
